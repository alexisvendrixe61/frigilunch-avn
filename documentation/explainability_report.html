System Overview

Frigilunch is an automated production planning system for a two-line ready-meal factory. Each weekly run reads open orders from an Excel workbook, assigns every order to a production day and line, builds a minute-by-minute shift schedule that respects real changeover times and allergen rules, and exports the result back to Excel. The planning horizon is rolling: the nearest four weeks are committed (locked) after every run, while everything further out is re-optimised from scratch the following week.

Most algorithm behaviour can be changed at run time by setting FRIGI_* environment variables — no code change required. The Tunable Parameters section explains each one and its business impact.

Pipeline Overview

Rolling Commit Mechanic

Each run commits the nearest COMMIT_WEEKS = 4 weeks. Committed days are frozen: the solver cannot move any order already placed there. Further-out weeks are re-optimised from scratch on every run.

Previous weeksCompleted
wk N (now)Committed — locked
wk N+1Committed — locked
wk N+2Committed — locked
wk N+3Committed — locked
wk N+4Open — re-optimised each run
wk N+5+Open — re-optimised each run

Committed days are stored in plan_state.json and replayed byte-for-byte at the start of the next run. A cold start (no state file) begins with an empty frozen set and plans the entire horizon from scratch.

The system reads open orders from Planning info.xlsx at run time. Each row is an order with article number, quantity, delivery date, and line preferences. Missing master data is cross-referenced against a product catalogue loaded from the same workbook.

Line Exclusion

Each product carries a prio_lijn block with per-line permission codes and an optional spiraal block for CFS (spiral-conveyor) products. The loader selects which block to use for line derivation:

line_source = p.get("spiraal", {}) if prio_lijn.get("cfs") == "voorkeur" else prio_lijn
line_info = derive_line_info(line_source.get("lijn1"), line_source.get("lijn2"), schaal, merk)

When prio_lijn.cfs == "voorkeur" (14 products), the spiraal field is used instead of prio_lijn. All 14 CFS products have spiraal = {lijn1: "kan_niet", lijn2: "kan"}, which resolves to l1_uitgesloten=True, alleen_l2=True — they are hard-locked to Line 2.

Why this matters: prio_lijn.lijn1 and prio_lijn.lijn2 are both "kan_niet" for CFS products. The 0/0 pair triggers a fallback in derive_line_info that treats both-forbidden as no restriction. Without the spiraal switch, CFS products could be placed on either line. With it, the hard L2-only constraint is correctly enforced by the solver's slot filter.

Stage 3 — Plan Lock

The planning horizon is split into two tiers with separate solver budgets. Frozen days from the previous run are loaded from plan_state.json before the solver starts — the solver cannot touch those days.

HorizonBudget (s)Max iterations
Committed (COMMIT_WEEKS=4 nearest weeks)24015
Open tail (beyond committed horizon)905

After the main solve, an incremental resolve pass (FRIGI_INCREMENTAL_RESOLVE=1) tries to backfill any order unplaced in Phase 1 or 2 by running a targeted re-solve with context from the already-placed orders.

Stage 5 — CP-SAT Optimizer

The core solver uses Google OR-Tools CP-SAT (constraint programming with SAT). It assigns orders to (day, line) slots and minimises a weighted objective. The solver runs in a feedback loop with the Oracle Day Builder: each proposed assignment is checked by the Oracle, and any order the Oracle cannot fit triggers a no-good cut that prevents the same assignment from being proposed again.

Feedback Loop

Phase Dispatch

Phase 1 — Line-restricted

Orders with alleen_l1 or alleen_l2 flags set. Placed first with hard line locks. FRIGI_TWO_PHASE_HARD_FIRST=1: hard constraints before softening.

Phase 2 — Flexible

All remaining unplaced orders compete for available capacity on either line within their legal slots.

Phase 3 — Split retry

Orders never placed in Phases 1–2 (FRIGI_RETRY_SPLIT_NEVER_PLACED=1) retried with forced splits: max FRIGI_MAX_CHUNKS=5 chunks, min FRIGI_MIN_CHUNK_MIN=60 min each.

Objective Function

The solver minimises a weighted sum. Completeness always dominates efficiency — an unscheduled order costs 10 000 points, making any scheduling penalty negligible by comparison.

cost = Σ unscheduled_orders × 10 000
     + Σ unscheduled_units  × 10   (FRIGI_UNSCHEDULED_UNIT_WEIGHT)
     + Σ efficiency_penalties

Off-priority line50Order placed on non-preferred line
Day activation2Each additional calendar day opened
Line activation5Each additional line activated on a day

Sate Exclusion (A5)

Any order with allergie_niveau ≥ 6 is sate. When FRIGI_SATE_EXCLUSIVE=1, the other production line must halt before the sate block starts. The sate block is slid to end-of-day (sate_last()) so the halt coincides with the natural shift end, minimising the capacity cost to the other line.

Staffing Ramp (P1)

Staff increases between consecutive orders are capped at max_bezetting_delta = 3 FTE. Only increases are capped — ramp-down is unrestricted. Orders with duration > 4 h (240 min) are exempt, as staff can arrive gradually during the order.

Device Contention (M1)

Single-unit devices serve only one order at a time. A FRIGI_PROXY_BUFFER_MIN=30 min gap is enforced between consecutive users. Single-unit devices: ks_menger, stephan_mixer_klein, stephan_mixer_groot, multifill, kaastrooi, multipond, isihda_l1, isihda_l2, grote_cfs_pomp.

Stage 7 — Day Sequencer

After CP-SAT assigns orders to days, the Day Sequencer finds the best within-day order for each line using a CP-SAT AddCircuit (TSP prize-collecting variant). Time limit: FRIGI_SEQUENCE_TIME_LIMIT = 2.0 s per line per day.

Objective

TermValueEffect
Positie bonus+1 000Reward for placing a must-first/last order in its required position
Kapvorm penalty (general)−50Penalise each kapvorm change between consecutive orders
Kapvorm penalty (L1 only)−2 000Strongly discourage kapvorm changes on Line 1 (preferred line)

Staffing Arc Pruning

Before solving, arcs (i → j) where the staff increase exceeds max_bezetting_delta = 3 FTE are removed from the circuit graph — unless order j has duration > 4 h (240 min), which exempts it. This prunes the search space while preserving all legal sequences.

After sequencing, the full DaySchedule is re-validated by the validator to confirm no hard constraints were broken.

Stage 8 — Post-solve Regroup

After a valid schedule exists, the campaign-regrouper clusters same-kapvorm orders onto the same day to reduce changeover time.

  • Campaign map: (line, kapvorm) → {day: order_count}
  • Move logic: An isolated kapvorm order (its kapvorm appears only on that day) is a candidate. The regrouper finds a target day that already has ≥ 1 order of the same kapvorm, within the order's delivery window. Both days are verified through the oracle after the move.
  • Swap fallback: If the target day is at capacity, one order from the target day moves to the source day to make room.

Stage 9 — Plan Scoring

Plans are compared lexicographically — a lower value on an earlier field always wins regardless of later fields. Lower is better for all fields.
